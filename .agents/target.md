# 被测环境：你被允许测什么

写用例之前先读这一篇。对着一个没开启的能力写用例，是这套验收里最浪费时间的做法——
代码写完、跑起来、红了，然后才发现测的东西压根不存在。

## 环境从哪来

默认是 `lab up` 起的一次性 Docker 栈，跑完 `lab down` 清空。**不显式传 `LAB_ENDPOINT`
就只打 `127.0.0.1`**，不会碰到任何共享环境——这是刻意的，别为了"方便"改掉它。

被测版本由镜像 tag 决定。CI 上的验收由发布方派发并带上确切的 release id；本地默认
`latest`。每次运行都会把镜像 digest 记进运行页，所以"这次测的是哪个构建"永远答得上来。

## 授权档位决定覆盖边界

被测实例跑在企业授权下，一部分能力开、个别关。**唯一的权威清单是
[`cases/smoke/instance-capabilities.case.py`](../cases/smoke/instance-capabilities.case.py)**，
不要在别的地方复述它——复述就会有两份，两份就会不一致。

那个用例做两件事：

1. **断言**当前用例集依赖的那几项开关，档位变了就红，并指名是哪一项。
2. **记录**整个 `limit` 对象进 artifact。所以一个还没人断言过的开关变了，也能在结果
   文件里看见。

要知道现在开了什么，有三条路，按顺序试：

```bash
uv run lab run smoke/instance-capabilities      # 跑一次，看 artifact 的 evidence.recorded
curl -s http://127.0.0.1:3100/api/instance/usage | python3 -m json.tool   # 直接问
```

或者翻最近一次运行的 `artifacts/<run-id>/smoke__instance-capabilities.result.json`。

**要测的能力是关着的怎么办**：不要写这个用例，也不要为了让它过去改断言。去问人——
是该开这个能力，还是这个方向本来就不在覆盖范围里。改 `instance-capabilities` 的断言
只有在**授权本身变了**的时候才对。

## 期望值必须实测得来

这条是花了代价换来的，写在这里避免第二次。

授权本身声明的档位是 `pro`（那是它作为产品卖出去时的名字），实例报出来的是
`business`。照授权推，用例照样红。

所以：**任何关于被测环境状态的期望值，都要先观察再写下来**，不要从文档、从配置、从
名字、从"应该是这样"推。观察一次的成本是几分钟，猜错的成本是一个红了却不知道为什么
的用例。

这跟"确定性数据"不冲突：**用例自己造的数据**由行号推导（见
[checklist.md](checklist.md)）；**环境本身的状态**靠实测。

## 只走公共 API

框架**不提供数据库连接**，这是刻意的，不是没做。

理由：用户是通过 API 用产品的。绕过 API 去数据库验证，能验出"数据在库里是对的"，
但验不出"用户读回来是对的"——而后者才是这套验收要回答的问题。中间那层缓存、序列化、
权限过滤，恰恰是最容易出错的地方。

所以别加数据库连接，也别为了"验证方便"去读 Postgres。compose 里那个暴露的 5432 端口
是给人排查用的，不是给用例用的。

## 授权会过期

授权有有效期。到期那天 `smoke/instance-capabilities` 会红，并且**指名是哪一项**，
不会让人在一堆失败里猜。

如果你看到那个用例红在 `level` 或那几个能力开关上，第一反应应该是"授权是不是过期
或者没配上"，而不是"产品是不是回归了"。
