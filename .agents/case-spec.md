# Case Spec 模板

从对方（可能只有片段的）输入起草，缺的自己补，写代码前拿去确认。**每个你推断的值
都标成假设。**

```md
## Case Spec: <group>/<case-name>

- **Goal**：这个用例能抓到什么回归，一句话。
- **Runner**：<runner kind>（复用 | 扩展 | 新写——说明是哪种，为什么）
- **Seed Phase**：要先存在什么状态。表结构、字段、行数、关联关系。
- **Execute Phase**：被测动作，有顺序地写。
- **Expectations**：逐条列出，每条写清在证明什么。
- **Data Determinism**：第 N 行的值怎么由 N 推导出来。
- **Cleanup**：这个用例造了什么，怎么删。
- **Open Assumptions**：你猜的每个值，标出哪些会改变实现。
```

## 填写规则

**Goal** 绑到真实产品动作。"抓住批量创建时 checkbox 空值语义的回归"，不是"测创建
记录"。

**Expectations** 是这份 spec 的重点，也是最容易写虚的地方。每条期望要能回答
"如果产品坏了，这条会怎么响"。写不出来的期望，多半没用。

至少覆盖三层：

1. **响应层**：状态码、返回的 id 数量、错误码形状。
2. **最终状态层**：通过真实读路径回验数据真的存在且正确。这一层是重点。
3. **副作用层**（有才写）：不该被改的东西没被改，不该出现的记录没出现。

只有第 1 层的用例基本没有价值——接口返回 200 但数据不对，是这类系统最常见的
故障形态。

**Data Determinism** 必须写出公式，不能写"随机生成一些数据"。值是行号的纯函数，
才能让 verify 本地推导期望值、让重跑可比、让失败可复现。

**Cleanup** 默认是"删掉 seed 建的 space"。如果这个用例故意留下什么，说明理由。

**Open Assumptions** 把会改变实现的那些排在前面：行数会不会让产品走另一条路径、
某字段的空值语义、并发下的顺序保证。

## 确认之后

写 `cases/<group>/<name>.case.py` 和同名 `.md`，在 `registry.py` 加一行，跑
`uv run lab check`，然后真跑一次并检查 artifact。流程见 [README.md](README.md)。
