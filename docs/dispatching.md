# 从发布流水线触发验收

这套用例回答的是"**这个** Teable 构建的接口对不对"。所以它应该在**镜像发布出来的时候**跑一次,
而不是定时跑,也不是谁改了 lab 的代码就跑。

这两件事的区别很实际:定时跑会在没有新构建的日子里重复测同一个东西,而漏掉两次发布之间的窗口;
按 lab 的代码提交跑,测的是"我改的 lab 有没有坏",跟产品有没有回归无关。

## 耦合方向

**这个仓库不去看别人的事件,而是对外开一个口,等别人来调。**

```
发布镜像的仓库                          teable-api-lab
─────────────────                      ──────────────
push / 发布完成
  → 算出这次的 tag
  → POST 到 api-lab 的 dispatch 口  ──→  按这个 tag 起环境、跑用例、验收
```

这样安排的三个理由:

1. **实验室是被动的。** 它不需要读任何其它仓库的事件流,也就不需要任何跨仓库的读权限。
   耦合是单向的,而且是从发布方指向实验室。
2. **"什么值得测"由发布方决定。** 路径过滤器、要不要跳过某类构建,这些判断只有发布方有信息。
   写在实验室里,发布方每次调整目录结构都要来改实验室。
3. **版本在派发的瞬间就钉死了。** 调用方传的是它刚推上去的**确切 tag**,不是 `latest`。
   一次运行永远绑定一个不会变的构建。

## 调用方式

```bash
curl -fsSL -X POST \
  -H "Accept: application/vnd.github+json" \
  -H "Authorization: Bearer $DISPATCH_TOKEN" \
  -H "X-GitHub-Api-Version: 2022-11-28" \
  https://api.github.com/repos/teableio/teable-api-lab/actions/workflows/acceptance.yml/dispatches \
  -d '{
        "ref": "main",
        "inputs": {
          "teable_image_tag": "<刚发布的确切 tag>",
          "case_filter": "all"
        }
      }'
```

- `ref` 是**用哪个版本的用例**去测,跟被测镜像无关。固定 `main`,除非你在验证用例本身的改动。
- `teable_image_tag` 传确切的 tag。**不要传 `latest`**——`latest` 会动,一周后没人说得清那次测的是哪个构建。
- `DISPATCH_TOKEN` 需要对本仓库有 Actions 的写权限,放调用方的 repository secret 里。
  派发前先判空,缺了就报错退出,否则 `curl` 会拿一个空 token 去撞 401,错误信息看不出是缺什么。

## 派发和手点长得一样

GitHub 把 API 派发和网页上手动点击都记成 `workflow_dispatch`,运行列表里分不出来。
如果需要区分(比如统计自动覆盖率),要靠调用方额外传一个参数,GitHub 本身不提供这个信息。

## 挂载点:挂在"对外可拉取"那一刻

流水线里"构建完成"和"镜像对外可拉取"经常**不是同一个时刻**。很多发布流程会先把镜像
推到内部仓库或 staging 通道,等到某次提升(promote)才拷到公开仓库。

挂错了后果很直接:派发出去的那一刻公开仓库上还没有这个 tag,`lab up` 直接拉不到。

所以判断标准只有一个——**在你打算挂的那个点上,`docker pull <公开仓库>:<tag>` 能不能成功**。
能,就挂这里;不能,就往后挪。

顺带一个好处:如果这个时刻正好是"某个构建即将成为 `latest`",那验收就从"事后知道坏了"
变成了"坏的构建进不了 `latest`"。代价是它挡在发布路径上,红了要有人处理——这是个流程
决定,不是技术决定。
